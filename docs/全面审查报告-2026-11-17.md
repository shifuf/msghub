# MsgHub 全面审查报告

审查日期：2026-11-17。基线：`37a4f17`。本次以检查与建议为交付，未修改业务代码、迁移、配置或锁文件，未连接真实数据库、发送通知或部署。

## 结论

项目已有完整的单管理员消息中台雏形，当前更需要补齐安全边界和消息可靠性，再增加渠道或扩展多人功能。不能以“能打包”作为上线充分条件：前端类型检查失败，消息清理存在误删条件，投递和定时任务存在异常中断/状态失真，配置备份不完整。

下列 28 个条目按可执行修复主题归组，其中既有确定缺陷，也有明确标注的运行条件风险及产品语义问题。依赖审计公告另列，不把所有公告都视为本项目可利用漏洞。

## 应优先修复

### 01. 高：后台消息 HTML 存在存储型 XSS 路径

- 位置：`apps/web/src/views/MessagesView.vue:179`、`:568`；`apps/api/src/openapi/simple-push.controller.ts:23`。
- 输入：持有项目 Key 的接入方可以提交 `html`；详情页取 `payload.html` 直接交给 `v-html`，未净化。
- 影响：管理员查看消息 HTML 时，事件属性等主动内容可能执行，读取同源 localStorage 中的管理 JWT 或调用管理 API。模板预览 `TemplateEditView.vue:70` 的 `srcdoc` iframe 也缺少 sandbox，导入不可信模板后存在同源执行风险。
- 建议：消息和模板预览使用禁止脚本的 sandbox iframe，并加 HTML 净化、URL 白名单及 CSP。隔离预览不能同时授予脚本与同源权限。
- 证据级别：源码完整数据流确认，未执行真实浏览器攻击。

### 02. 高：无效清理日期可能删除全部消息

- 位置：`apps/api/src/messages/messages.service.ts:1886`；`apps/api/src/messages/dto.ts:141`。
- `before: "not-a-date"` 可通过字符串校验；服务忽略无效时间，但随后只判断 `before` 是否非空，最终 `deleteMany({where:{}})`。
- `clear()` 和活动日志清理也有“无效日期忽略条件”的同类模式。
- 建议：DTO 使用日期校验，服务解析失败必须 400；删除前返回预览数量；清理只允许终态记录，避免队列引用被提前删掉。
- 证据级别：隔离复现已得到空删除条件，未执行真实删除。

### 03. 高（部署条件）：公开默认 JWT 密钥仍可在生产启动

- 位置：`docker-compose.yml:54`、`:57`；`apps/api/src/auth/auth.module.ts:16`；`jwt.strategy.ts:12`。
- Compose 和代码提供公开签名密钥回退，未做生产启动拒绝；示例管理员密码也可直接使用。
- `JwtStrategy.validate()` 不检查 sub、用户存在性或账号状态；使用公开默认密钥签发的任意有效 JWT，可以进入只依赖 Guard 的管理接口。
- 建议：生产强制非默认随机密钥和安全初始化凭据；JWT 校验用户及会话版本。
- 证据级别：默认值/校验流程源码确认，隔离复现确认 validate 接受无 sub 的 payload；未读取实际部署密钥，不能断言当前线上使用默认值。

### 04. 高：修改密码不能撤销旧会话

- 位置：`apps/api/src/auth/auth.service.ts:48`、`jwt.strategy.ts:16`、`realtime/realtime.controller.ts:17`。
- 改密码仅更新 passwordHash，旧 JWT 直到到期仍有效（默认 7 天）；SSE 仅建连时验签，连接持续期间也没有重新认证。
- 建议：增加 tokenVersion/passwordChangedAt 或服务端 session，密码变更撤销旧会话并断开流；SSE 改为短期专用票据，避免长期 JWT 出现在 URL 和访问日志。

### 05. 高：渠道抛异常会中断完整兜底链

- 位置：`apps/api/src/messages/messages.service.ts:501`、`:1034`；`queue/send.processor.ts:180`。
- 项目策略只处理返回 `success:false` 的失败，没有按渠道捕获异常。多个适配器在 try 外执行配置校验，Webhook 模板编译也可能抛异常。
- 影响：首个渠道异常时，第二渠道、管理员邮件、站内兜底均可能不执行；已经创建的日志停在 PENDING。队列处理器的异常也绕开自定义状态更新/兜底分支。
- 建议：统一适配器错误边界，所有异常写入尝试记录再进入下一渠道；队列 failed 事件兜底更新数据库状态。
- 证据级别：隔离复现确认首个渠道抛异常时三个后续步骤均未调用。

### 06. 高：执行中的定时任务在重启后永久悬挂

- 位置：`apps/api/src/schedules/schedules.service.ts:119`、`:139`。
- 领取任务改为 RUNNING；进程崩溃后只有 PENDING 会再次扫描，无 lease、heartbeat、超时恢复。
- 影响：普通定时消息、静默补发、未读邮件兜底都可能永久不再执行。
- 建议：有期限的任务租约、恢复扫描和稳定幂等标识。发送后/写回前崩溃有重复风险，不能只把所有 RUNNING 粗暴改回 PENDING。
- 证据级别：全源码无 RUNNING 恢复路径，隔离复现确认扫描仅匹配 PENDING。

### 07. 高：定时取消存在竞争，已发送却显示“已取消”

- 位置：`apps/api/src/schedules/schedules.service.ts:102`。
- cancel 先查询 PENDING，再按 id 无条件 update。两步之间执行器可领取并发送任务，取消随后覆盖状态。
- 建议：取消使用 `updateMany where id + status=PENDING` 条件更新并检查 count；执行中明确提示不能保证撤回。
- 证据级别：隔离交错执行复现：发送次数 1，最终状态 CANCELLED。

### 08. 高：备份恢复不能还原当前配置

- 位置：`apps/api/src/backup/backup.service.ts:57`、`:113`、`:493`。
- 项目未导出/导入 `unreadEmailFallbackEnabled`、等待时间、兜底模板；定时任务丢失 channelId/channelType；PartnerLink 未导出；抑制名单只取 5000 条。
- 未读兜底任务依赖原 MessageLog，但备份只保留变量中的旧 sourceMessageId，不恢复日志，新实例会以 source_missing 跳过。
- 建议：定义备份版本与完整字段清单、实体引用映射；区分“配置迁移”与“完整灾备”；无法恢复的运行中任务显式排除并报告，不能静默视作成功。
- 证据级别：隔离导出复现确认项目字段和渠道丢失；其他缺项由 schema 与导出结构比对确认。

### 09. 高：备份按名称关联会合并不同实体，重复导入会重复任务

- 位置：`apps/api/src/backup/backup.service.ts:210`、`:216`、`:326`、`:493`；schema 的 Project.name / Channel.name 无唯一约束。
- 同名项目被 Map 覆盖，配置/模板/绑定混入另一项目；找不到 projectName 的模板/抑制名单会降级成全局；每次导入定时任务直接 create。
- 导入也缺少整体预检、事务、冲突预览，后段失败时前段修改已经生效。
- 建议：备份内部稳定 ID、严格引用验证、dry-run 差异预览、明确合并策略和事务、任务导入幂等。渠道凭据以明文导出，应提供可选择的脱敏/加密导出。

### 10. 高（并发）：每日邮件配额不是原子操作

- 位置：`apps/api/src/email-policy/email-policy.service.ts:68`。
- 先 count，随后发送流程再建日志；并发请求可同时读到旧计数。
- 建议：在明确业务时区下原子预占每日配额，失败按策略归还，重试不重复扣费。
- 证据级别：隔离复现配额为 1，3 个并发调用全部通过。真实数据库并发还需集成测试。

### 11. 中高：反向代理后不同用户共用 IP 限流桶

- 位置：`apps/api/src/main.ts:13`、`app.module.ts:55`、`apps/web/nginx.conf:18`。
- 默认 ThrottlerGuard 使用 `req.ip`；Express 未设 trust proxy。Nginx 虽转发 X-Forwarded-For，API 仍按代理 IP 识别请求。
- 影响：同一路由所有外部用户共享限制；攻击者可消耗登录/发送接口额度，正常用户得到 429。这里是按路由的桶，不是整个站点共用一个桶。
- 建议：仅信任实际代理网段/层数并清洗转发头；开放 API 按项目 Key + 来源限制；全局规则使用共享存储。不要直接无条件 trust proxy=true。

### 12. 中高：IPv4 映射 IPv6 可绕过内网地址拦截

- 位置：`apps/api/src/adapters/http.util.ts:46`、`:83`。
- URL 将 `::ffff:127.0.0.1` 标准化为 `::ffff:7f00:1`，检查把尾部当普通文本而没有解析成 IPv4，随后因为 isIP 非零跳过 DNS 检查。
- 影响边界：需要能配置出站 URL 的权限，通常为管理员或导入配置者，不是任意匿名请求者。
- 建议：可靠 IP 解析库覆盖映射地址与完整 IPv6 内网段；连接复用校验得到的地址，防止 DNS 校验和实际 fetch 二次解析之间的重绑定。
- 证据级别：仅执行校验，确实接受环回 URL；未访问内网目标。DNS 重绑定为待集成验证风险。

## 消息状态、前端和 API 缺陷

### 13. 中高：铃铛已读与服务端已读不一致

- 位置：`apps/web/src/stores/notify.ts:122`、`:208`、`:216`；`apps/api/src/messages/messages.service.ts:1618`。
- 铃铛读取/全部已读只改 localStorage，忽略服务端 readAt；没有调用已有 mark-read API。
- 影响：跨设备不一致，已读计数错误，用户已在铃铛阅读却仍触发未读邮件兜底。
- 建议：服务端 readAt 作为统一状态；点击和全部已读调用 API，成功后更新本地并用 SSE 同步。
- 证据级别：隔离执行真实 store，server readAt 已有值但 unreadCount 仍为 1。

### 14. 中：PENDING 变 FAILED 不会再产生失败弹窗

- 位置：`apps/web/src/stores/notify.ts:87`。
- 已存在 id 的消息更新后立即 return，未加入 freshQueue，也不触发 desktop notification。后端在发送前就 publish PENDING，所以之后的失败通常落入这条路径。
- 建议：按 id + 状态版本去重，仅在关键状态转移时通知；SSE 的重复事件监听也应合并。

### 15. 中：SSE 重连和轮询不能完整补偿漏消息

- 位置：`apps/web/src/stores/notify.ts:160`、`:179`；`apps/api/src/dashboard/dashboard.service.ts:80`；`realtime/realtime.service.ts:12`。
- 重连后直接停止轮询，没有补拉断线窗口；轮询仅比较 createdAt 且最多 20 条，遗漏老消息状态更新和突发流量中的中间记录；内存 Subject 无多实例广播。
- 建议：事件序号/游标、Last-Event-ID 或 updatedAt+id 增量分页；重连先补齐；多实例通过 Redis 广播；轮询批次按时间升序合并。

### 16. 中：全局异常过滤器破坏结构化错误

- 位置：`apps/api/src/common/http-exception.filter.ts:26`；`openapi/simple-push.controller.ts:454`。
- 控制器抛 `{error:{code,message},data}`，过滤器却把整个 error 对象放入 code，丢弃实际 message 和 data。
- 影响：429/409/502 显示“服务器内部错误”，发送失败的 messageId 丢失，接入方难以正确重试。
- 建议：兼容 Nest 原生异常和统一业务 envelope，保持 code 为字符串、保留安全业务 data；普通 500 不向外返回原始数据库错误文本。
- 证据级别：隔离复现确认 code 为对象、message 被替换、data 变 null。

### 17. 中：前端 6 处类型错误被打包脚本绕过

- `apps/web/src/App.vue:8`：boxSizing 被推断为普通 string。
- `apps/web/src/layouts/AdminLayout.vue:320`：通知 API 类型不支持传入的 onClick；需用组件支持的 action/content 渲染交互，并实测点击行为。
- `apps/web/src/views/TemplatesView.vue:27`、`:31`；`PushTemplatesView.vue:43`、`:47`：NSelect 传 boolean 值及 boolean options，不符合组件 value 类型。
- 建议：用字符串/数字枚举筛选后映射布尔值，明确 CSSProperties；build 前执行 vue-tsc --noEmit 并纳入 CI。
- 证据级别：实际类型检查失败；不能仅凭类型错误断言所有对应交互在浏览器必然失败。

### 18. 中：系统停机后每日任务短时间内连续补发

- 位置：`apps/api/src/schedules/schedules.service.ts:225`。
- 成功后按旧 runAt +24h 重排，停机数天恢复后下一执行时间仍在过去，每个 tick 再发一次，直到追平；任意非空 cron 都被当作 daily。
- 建议：明确错过执行的策略（跳过、合并一次、限速补齐），计算未来执行点，校验 cron=daily 或实现真正 cron/时区语义。
- 证据级别：隔离复现四天前任务执行后，下一次仍落后两天以上。

### 19. 中：自动健康检查会持续发送真实测试通知

- 位置：`apps/api/src/channels/channel-health.service.ts:24`、`:57`、`:86`；各适配器 test()。
- 默认十分钟 probe，直接调用 adapter.test；多数渠道 test 就是 send 测试文案。一个默认启用的推送渠道一天可收到约 144 条健康测试通知；Webhook 会调用真实业务目标。
- 建议：无副作用 probe 与人工测试发送分开；不支持探测的渠道默认关闭主动发送；提供每渠道频率/启停 UI，探测异常要在定时入口捕获。

### 20. 中：时区非法值导致普通消息派发报错

- 位置：`apps/api/src/projects/dto.ts:99`；`common/quiet-hours.service.ts:98`。
- quietTimezone 仅校验 string，非法 IANA 时区可保存；Intl.DateTimeFormat 抛 RangeError。开启静默时低/普通优先级投递在发送前失败。
- 建议：保存时验证时区、提供合法时区选择；历史坏数据给予明确错误和安全修复路径。
- 证据级别：隔离复现已抛 RangeError。

### 21. 中：CSV 导出保留可执行公式

- 位置：`apps/api/src/messages/messages.service.ts:200`。
- escape 仅处理逗号/引号/换行；接入方可提交以 `=` 等开头的标题，导出后被电子表格解释为公式。
- 建议：对不可信文本列进行公式前缀防护，或使用明确文本单元格的 XLSX；仅双引号转义不足以阻止公式。
- 证据级别：隔离导出 `=1+1` 未转为文本；未执行外连/系统命令类公式。

### 22. 中：全局事件 code 缺少真正唯一性

- 位置：`apps/api/prisma/schema.prisma:149`；`events/events.service.ts:50`。
- PostgreSQL 普通复合唯一约束允许多个 NULL projectId + 相同 code，创建事件未先查全局重复；dispatchEvent 用 findFirst，重复配置使选择不确定。
- 模板/抑制名单也存在 nullable scope 的同类数据库约束问题，应用层先查再建不能防并发。
- 建议：全局 scope 部分唯一索引或非空 scopeKey，并先清理重复数据。

### 23. 中：模板缺必填变量时仍可能发送空内容

- 位置：`apps/api/src/messages/messages.service.ts:856`、`:1338`。
- 只有变量对象非空才校验；完全不传 variables 或传 {} 会跳过。验证码 code 又被全局 optional 集合忽略，不能保证登录模板有验证码。
- 建议：按模板明确 required/optional；无论是否传变量都做校验；条件分支字段按模板语义处理，不能全局把 code 标成可选。

### 24. 中：邮件退订链接和未读等待单位的文档不准确

- 位置：`apps/api/src/messages/messages.service.ts:1325`；`common/env.ts:35`；`docs/对接开发文档.md:182`；schema 的 unreadEmailFallbackHours 注释。
- 生产未设置 SITE_URL 时生成 `/unsubscribe?...` 相对链接；邮件客户端没有本服务页面 origin，无法靠浏览器当前域名自动补全。
- 未读字段名为 Hours，实际实现和后台 UI 为分钟，文档仍称默认 24 小时，接入方按文档会提前 60 倍触发。
- 建议：外发邮件要求可用绝对站点 URL；增加明确 Minutes 字段并提供兼容迁移，统一文档和默认值，不直接改变旧数据含义。

### 25. 中（语义）：邮件已发送被当作用户已阅读

- 位置：`apps/api/src/messages/messages.service.ts:1848`。
- SMTP 成功后原推送 readAt 自动写当前时间，且阻止重发；SMTP 接受不等于用户阅读。
- 建议：拆分 deliveredAt、readAt、fallbackSentAt，展示“已邮件兜底”而非“已读”。若这是既定业务策略，至少在统计和 UI 明确标记，不混用阅读指标。

## 运维与可维护性

### 26. 中高：数据库/队列之间缺少可恢复的一致性边界

- 位置：`apps/api/src/messages/messages.service.ts:387`、`:455`；`queue/send.processor.ts:137`。
- 先落库后入队，崩溃可能遗留 PENDING；处理器发送前未以已完成消息做幂等跳过；清理可以删除仍被 job 引用的日志，外发后写状态失败可能导致重试重复发送。
- 幂等记录 commit/release 没有租约所有者标识，请求超过 TTL 后旧请求可能修改新占用；成功外发后 commit 失败又释放会让重试重发。该长尾需要故障注入验证。
- 建议：事务 outbox、稳定 jobId、独立“消息/投递尝试”模型、运行记录清理保护；外部服务支持时使用其幂等键。不能承诺跨外部网络严格 exactly-once。

### 27. 中：健康状态、构建和初始化不够可预测

- `/api/health` 只检查 PostgreSQL，不检查 Redis/worker/积压，队列不可用仍可能显示健康。
- `apps/api/Dockerfile:12` 允许变动 lock；runner 再次 npm install 且没有 npm 锁文件；web Dockerfile 不复制 pnpm-lock。部署依赖可能与本次审计不同。
- `apps/api/prisma/seed.js` 与 seed.ts 的默认邮件模板不一致（Docker 注册/重置模板缺少开发版链接逻辑）；entrypoint 把 seed 失败当非致命，可能健康但没有可登录管理员。
- 未设置 enableShutdownHooks，退出时 service 的 destroy 清理不能保证由 Nest 信号流程触发；无 Docker 集成验证。
- 建议：统一锁定依赖和 seed 来源；初始化失败阻止就绪；拆 liveness/readiness 并覆盖队列；在目标 Node/Docker 版本验证迁移、冷启动、升级、重启。

### 28. 中：规模增长后缺少自动保留策略、分页和聚合

- `SchedulesService.list()` 全量返回，历史任务无限增长；Dashboard.charts() 将窗口内所有日志加载到内存再聚合；IdempotencyService.cleanupExpired() 未见调用。
- 默认生产 CORS 反射任意 Origin 并允许 credentials，虽然当前主要使用 Bearer 并不能直接据此断言 CSRF，但策略过宽，建议同源/明确白名单。
- 自定义 ADMIN_PATH 只是路由入口，公共 config.js 和未登录访问 /dashboard 的跳转可获知，不能当作安全鉴权措施。
- 建议：任务分页、DB groupBy/SQL 聚合、按项目保留和归档、定期幂等记录清理、合适索引与查询计划检查。记录脱敏、最大正文/响应限制也应纳入容量控制。

## 建议增加的功能与顺序

### 第一阶段：可靠投递和安全基础

1. **统一消息状态和投递时间线**：接收、排队、发送、失败、兜底、已读分别建模；每次尝试有独立记录，能看到为何切渠道。
2. **任务恢复与投递控制台**：租约恢复、重试/死信、取消竞争处理、积压告警；现有 queue-admin 代码可复用，重点补可靠性和可见性。
3. **通知中心统一已读**：服务端同步、跨设备同步、断线补拉、失败状态提醒、明确已读和已兜底的区别。
4. **备份预览与恢复演练**：完整性校验、冲突预览、事务恢复、重复导入保护、加密/脱敏选项、定期恢复验证。
5. **安全会话与配置检查**：弱密钥拒绝启动、改密撤销会话、可选 TOTP、短期 SSE 票据、危险 HTML 隔离。
6. **自动化质量门禁**：后端测试、vue-tsc、lint、依赖扫描；真实 PG/Redis 的重启/并发/幂等/静默/兜底集成测试。

### 第二阶段：日常使用和运维效率

1. **定时任务编辑、暂停/恢复和时区**：明确错过执行策略，支持按需真正 cron；不必一开始支持复杂工作流。
2. **按项目送达指标和告警**：队列等待、端到端时延 p95、外发成功率、兜底率、超时、渠道配额；业务成功与站内降级成功分别统计。
3. **数据保留和脱敏**：自动归档/清理、验证码等敏感正文短期保留、删除预览与审计。
4. **接入调试工具**：OpenAPI schema、请求样例、幂等冲突解释、签名验证、无副作用 dry-run、可靠的错误码。
5. **模板编辑保障**：必填变量 schema、实时校验、草稿/发布、版本回滚和隔离预览。
6. **配额与批量发送预览**：原子额度、批量受众校验、预估次数、逐项结果导出。

### 第三阶段：视实际需求再扩展

- 只有确实给多人使用时增加 RBAC、项目授权、审批和多租户隔离；当前产品明确为单管理员，不能仅加用户表就宣称支持多租户。
- 移动端设备管理与真实点击回执：Bark/Gotify 适配器没有自动把服务生成的 messageId/readToken 注入兼容的点击回执流程，仅凭手机打开通知无法保证更新本平台 readAt。
- 重要业务需要时再加通知聚合、升级告警链、双渠道并发、维护窗口和短信；先解决丢消息/重复发送，再扩展更多通道。

## 推荐落地次序

优先处理 01–07、10–13、16，阻断接管后台、误删、停机漏发和明显状态错误；同步修前端类型错误并锁定构建。随后完成备份恢复、通知一致性、定时策略和无副作用健康检查。最后进行真实 PostgreSQL/Redis 的故障注入与 Docker 部署回归，再排新功能。

每项修复应使用能触发该问题的回归用例验收；本次 `scripts/audit-repro.cjs` 可作为其中部分用例的起点，数据库事务、浏览器 XSS 隔离和第三方送达仍需对应环境测试。
